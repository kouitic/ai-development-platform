# 要件分析

## レビュー対応後の完了定義

本基盤の状態は「MVP foundation complete」「Operational MVP incomplete」とする。設定、CLI骨格、Mock Provider、SQLite、決定的状態遷移、初期化・検証、セキュリティ方針、テンプレート、Mock Workflow試験はfoundationに含む。実Claudeによる変更、実GitHubのIssueからPR・Checkまで、実Actionsレビュー、実行時サンドボックス、限定E2Eは、コードが存在しても外部受入が完了するまでOperational完了に含めない。

第3回レビュー後もOperational MVP完了ゲートは次の13条件を維持する。従来のOPM-001〜015は機能追跡IDとして維持し、正式要件ID単位の完全なTraceability、Python 3.12/3.13 CI、Mock/Claude依存分離、クリーンSource Packageを各条件の証拠へ追加する。

1. AIコード変更後にホストVerificationを実行する。
2. Verification成功後だけcommitする。
3. Verificationを変更ファイル、diff digest、基準SHA、commit SHAへ結び付ける。
4. System、Business、QAを重複なく順番に実行する。
5. 全レビューを同一PR head SHAへ固定する。
6. Business ReviewはSystem Reviewの無条件PASSを前提とする。
7. QAは両レビューとtrusted verificationを前提とする。
8. Findingをorigin種別、状態、候補SHA、解決review、acceptance evidenceで追跡する。
9. 未実装ToolをAgent設定に宣言しない。
10. 実ClaudeのGitHub安全条件を自己申告環境変数だけに依存しない。
11. 検査済みのクリーンな正式ソースZIPを生成できる。
12. Mock E2Eで変更、検証、commit、PR、review、rework、再検証を再現する。
13. 実Claude＋実GitHub限定受入でAI変更後のホスト検証成功を確認する。

## 1. 要約

本基盤は、1つのGitHubリポジトリに対するシステム開発を、対話、設計・開発、システムレビュー、業務レビュー、QAの各AIが分担して進めるPython製CLIである。確定要件、コード変更、正式レビュー、品質評価はGitHubに記録し、未確定会話と実行状態はローカルSQLiteに保存する。mainへのマージ、本番デプロイ、本番データ変更などの重大操作は、人間の明示的な承認なしには到達できないようにする。

品質に関する標準表現は「定義された品質基準を満たしています」とし、AIが最終品質を保証する表現は用いない。AIは証拠を収集して適合状況を示し、最終判断と残存リスクの受容は人間が行う。

## 2. 利用者と責任分担

- 主利用者は、ITの基礎概念は理解するが実装経験が少ない人を想定する。
- 人間は業務目的、業務要件、期待結果、品質基準、ガバナンス、重大な承認を決定する。
- AIは承認済み情報を仕様化し、設計、実装、テスト、レビュー、証拠収集を行う。
- 対話AIは技術選択を、業務、利用者、費用、運用、セキュリティ、停止時間、データへの影響に翻訳する。

## 3. MVP対象

- Python 3.12または3.13（3.14未満）、uv、Typer、Rich、Prompt Toolkitによる`ai-dev` CLI
- `init`、`validate`、`doctor`、`chat`、`ask`、`run`、`status`、`pause`、`resume`、`cancel`、`approve`、`reject`、`logs`
- PydanticモデルとJSON Schemaで検証するYAML設定
- AgentProvider抽象、ClaudeAgentProvider、MockAgentProvider
- 対話、設計開発、システムレビュー、業務レビュー、QAの設定可能な5役割
- LangGraphを利用する構造化ワークフローと最大3回の修正反復
- SQLiteによる状態、監査イベント、承認の保存と再開
- GitHub Issue候補作成、Issue作成、ブランチ作成の抽象化
- 人間承認待ち、工程境界での停止、完了後の変更Issue
- Secretおよび本番相当データの混入検査
- GitHubテンプレート、最小権限のActions雛形、CODEOWNERS
- Mockのみで外部APIなしに実行できる自動テスト
- セットアップ、開発、運用、QA、トラブル対応文書

## 7. 不明点と採用する前提

| 不明点 | MVPでの前提 |
|---|---|
| Claude Agent SDKの認証・モデル | 環境変数で与え、Mockを標準実行経路にする。実接続は明示選択時のみ行う |
| GitHubリポジトリと組織ポリシー | `gh` CLI経由のアダプターを用意し、ローカルMockを提供する。管理設定の自動変更はしない |
| デプロイ先 | この基盤自身はローカルCLIとして提供する。開発対象システムのデプロイ先はIssueごとに確認する |
| 業務評価基準 | プロジェクトのYAMLで人間が承認した基準を設定する。未定義時はPASSにしない |
| コストの取得 | Providerが返す利用量から推定し、取得不能なら推定または不明と明示する |
| ブランチ保護等の確認 | `doctor`で確認可能な範囲を報告し、未確認と不合格を区別する |

## 8. 矛盾と解決方針

重大な矛盾はない。次の緊張関係は設計で解消する。

1. 業務レビューAIには広いWeb閲覧を許可する一方、外部APIやデータ送信を制限する必要がある。閲覧能力と送信能力を別権限とし、外部コンテンツを常に未信頼データとして扱う。
2. `.ai-dev/**`は保護対象だが、`init`は同領域を生成する必要がある。初期化専用の信頼済みサービスのみが新規生成でき、通常エージェントの変更対象からは除外する。
3. Actions定義は初期生成対象かつ保護対象である。テンプレート生成は許可し、生成後の変更は人間承認対象とする。
4. autonomousモードでも重大操作の承認は省略できない。モードは工程内の確認頻度だけを変更し、強制承認ゲートは変更しない。

## 9. 主なリスク

- LLM自由文の誤解釈による不正遷移: 構造化結果、Schema、状態遷移表、権限検査を重ねる。
- プロンプトインジェクション: 外部入力を命令から分離し、ツールとデータ送信をポリシーで制限する。
- Secret混入: 初期化、validate、pre-commit、CI、ログマスキングの複数層で検査する。
- 本番相当データ漏えい: パス、分類、保存先、エージェント役割、実行環境の各層で拒否する。
- AI自身による基準緩和: 保護パス、CODEOWNERS、承認記録、コミットSHA固定で防ぐ。
- 外部SDK/API変更: ProviderとGitHub Gatewayで隔離し、Mockテストを維持する。
- コスト・反復の暴走: ターン数、時間、反復、タスク・月次予算を強制上限にする。
- Windows/Linux差異: `pathlib`とPython APIを利用し、シェル依存をアダプターに閉じ込める。

## 10. 技術・セキュリティ・データ制約

- Python 3.12以上3.14未満、パッケージ管理はuv、CLIは常駐サーバーを要求しない。
- ドメイン層はTyper、GitHub、Claude、SQLiteから独立させる。
- AI自由文は状態遷移命令にしない。検証済み列挙値だけを受け付ける。
- 上位ポリシーの禁止事項を下位設定で緩和できない。
- Secret値、本番相当データ、資格情報は会話、SQLite状態、Artifact、通常ログへ保存しない。
- 実GitHub、実Claude、ネットワーク、本番操作は明示選択と必要な資格情報がある場合だけ実行する。

## 11. 人間承認が必要な箇所

業務要件と業務ルール、品質基準、期待結果、デプロイ先、本番構成、外部サービス、Agent定義・プロンプト、CI/CD、Secret/IAM/ネットワーク、破壊的DB変更、本番相当データ、既知リスク、mainマージ、本番デプロイ・データ変更、ロールバックを承認対象とする。承認はIssue、工程、コミットSHAが一致した構造化記録だけを有効とする。

## 12. 将来拡張ポイント

Agent Provider登録、エージェント定義、ワークフローノード、レビュー種別、データ分類、GitHub Gateway、状態Store、品質ゲートをインターフェースまたは設定で追加可能にする。禁止事項の緩和は拡張ポイントに含めない。
