# リポジトリ規約の適用範囲

## 1. 目的

`ai-development-platform`には、性質の異なる二つのリポジトリ規約があります。本書は、プラットフォーム自体の保守規約と、プラットフォームが対象システムへ強制する開発規約を分離し、誤適用を防ぐための境界文書です。

## 2. 二つのパターン

| 区分 | パターン①：プラットフォーム自体の開発 | パターン②：プラットフォームを利用するシステム開発 |
|---|---|---|
| 対象 | `ai-development-platform`リポジトリの保守・機能開発 | `ai-dev init`で初期化された対象システムの開発 |
| 主な実行者 | 人間とCodex | 設計開発AI、System Review AI、Business Review AI、QA、ホストサービス、人間 |
| 作業トリガー | 人間のチャット・添付・明示指示 | 承認済みの正式GitHub Issue |
| 通常ブランチ | `main` | `ai/issue-<number>-<description>` |
| main直接変更 | 人間の明示指示により許可 | AIには禁止 |
| 作業ブランチ | 必須ではない | 必須 |
| PR | 必須ではない | 必須 |
| マージ | 人間の明示指示によりmainへ直接反映可能 | 必須Checkとレビュー後に人間が承認し、人間または信頼済みGitHub機構が実行 |

## 3. パターン①：プラットフォーム自体の開発

パターン①は、開発効率を保ちながら、人間がCodexの変更範囲とGit操作を管理するための規約です。

1. 人間のチャット指示、添付指示または明示的な作業依頼を作業開始の根拠とします。
2. Issue、作業ブランチ、PRは必須ではありません。
3. 通常はmain上で作業できます。
4. 実装依頼はファイル変更を許可しますが、コミットとプッシュは自動では行いません。
5. 人間がコミット、プッシュまたはmainへの反映を明示した場合は、検証済み変更をmainへ直接反映できます。
6. 人間が別ブランチやPRを指定した場合は、その方式を使用します。
7. 変更範囲に応じたテスト、静的検査、設定検証、Secret/Data scan、Git状態確認を維持します。
8. Secret、本番相当データ、未関連変更、破壊的操作に対する安全制御は、ブランチ戦略と無関係に維持します。

パターン①の実行規約の正本は、リポジトリルートの`AGENTS.md`です。

## 4. パターン②：プラットフォームを利用するシステム開発

パターン②は、複数AIの権限を分離し、要件からレビューまでの証拠を人間の最終判断へ結び付けるための規約です。

1. AIの変更作業は、承認済みの正式Issueを必須トリガーとします。
2. Issue番号、要件ダイジェスト、対象commit SHA、受入条件を固定します。
3. 設計開発AIはmainを変更、push、mergeできません。
4. AIの変更は、Issueに対応する許可済み作業ブランチだけで行います。
5. AIへGitの直接操作権限を渡さず、ホスト側Gatewayが変更内容とVerificationを検証した後だけcommitと作業ブランチpushを行います。
6. 作業ブランチからPRを作成し、Issue、変更、テスト、Traceability、レビュー証拠を関連付けます。
7. System Review、Business Review、QAは対象要件とcommit SHAを固定し、それぞれの権限範囲で独立評価します。
8. AIは自己承認、main直接push、force push、PR自己マージを実行できません。
9. 必須Checkとレビューが完了しても、人間の承認なしにmainへマージできません。
10. Issue本文、要件ダイジェストまたは対象SHAが変わった場合は、古い承認と証拠を無効化し、必要な工程を再実行します。

パターン②の詳細な正本は、`docs/development-workflow.md`と`docs/github-configuration.md`です。生成先AI向けの要約は`src/ai_dev_platform/templates/project/AGENTS.md`、実行時の機械的制約は`.ai-dev/`と生成テンプレート内の`.ai-dev/`で管理します。

## 5. 適用判断

次の順序で適用する規約を判断します。

1. 変更対象がプラットフォーム自体か、プラットフォームが扱う対象システムかを確認します。
2. 人間とCodexがこのリポジトリを保守する場合は、パターン①を適用します。
3. `ai-dev`のWorkflowや各AIが対象システムを変更・評価する場合は、パターン②を適用します。
4. パターン②を実装・修正するために、このリポジトリの製品コードやテンプレートをCodexが変更する作業そのものには、パターン①を適用します。
5. ただし、パターン①で製品コードを変更することを理由に、パターン②の安全制御を暗黙に緩和してはいけません。

ルート`.ai-dev/`はパターン②の動作を自己検証するための製品設定であり、Codexによるパターン①のGit操作を直接禁止する上位規約ではありません。

## 6. 代表例

| 依頼 | 適用 | 扱い |
|---|---|---|
| 「CLIの不具合を直して」 | パターン① | IssueやPRなしで修正可能。コミット・プッシュは明示指示待ち |
| 「修正をmainへプッシュして」 | パターン① | 検証後、mainへ直接コミット・プッシュ可能 |
| 「この機能を対象システムへ実装して」 | パターン② | 承認済みIssueと作業ブランチが必要 |
| 「設計開発AIが作ったPRを評価して」 | パターン② | commit SHAを固定し、独立レビューとQAを実行 |
| 「生成テンプレートのmain保護を強化して」 | 作業はパターン①、成果物はパターン② | このリポジトリは直接修正可能だが、生成先のAI制約は厳格に維持 |
